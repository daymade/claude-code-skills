# Turn evidence into valuable action

Compare observed-defect repair, value/repeat-use improvement, qualified acquisition,
economic improvement and doing nothing. Explain which evidence changes the ordering.
Estimate opportunity only with exposed population, recoverable loss, unit value and
cost assumptions; show ranges/sensitivity. Avoid arbitrary confidence-score precision.

Run research and repair in parallel when appropriate. Fix an authorized reproduced
broken entry without waiting to prove total growth impact; continue distribution
learning. Avoid an unsupported product-wide no-promotion-until-perfect gate.

## Write an action card

Specify each selected action's:

- Observed problem/opportunity, source, affected population and missingness.
- Mechanism hypothesis and evidence that would overturn it.
- Smallest useful change/learning action and implementation owner.
- User/business outcome, baseline definition and meaningful improvement threshold.
- Comparison, assignment/analysis unit, window and uncertainty.
- Cost, guardrails, downside and delayed effects.
- Authorized executor, decision date and continue/change/stop criterion.
- Consumer-side implementation readback and later business-result evidence.

Fit the set to actual capacity. Ask only for missing product tradeoffs or authorization
after preparing concrete alternatives/consequences. Do not send messages, alter
production, buy traffic or change pricing to complete an analysis card.

## Verify separate layers

1. Reproduce failure or establish baseline for the relevant version/environment;
   include a healthy control when diagnosing a defect.
2. Verify the delivered change at the actual customer/public entry, permission
   context and supported platform; identify untested environments.
3. Observe intended task results with real users or permitted task evidence;
   distinguish maintainer smoke tests from external adoption.
4. Measure scoped growth/business effect with the agreed design and mature window;
   report beneficial, harmful, null and inconclusive results honestly.
5. Decide continue, revise, roll back or stop against value and guardrails. Update
   the existing project record; retain failed hypotheses only when they alter
   future decisions.

Never equate published code, closed issues, successful installation, dashboards or
reviewer agreement with retention/revenue improvement. Do not wait indefinitely
for absent feedback: name the unknown effect, missing observation, recovery action
and reconsideration point.
