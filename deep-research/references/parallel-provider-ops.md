# Parallel provider research

Load this when one decision question is assigned to two or more AI products or modes. `deep-research` coordinates the business question, agent assignments, source checks and synthesis. Each surface owner composes the current provider Skill with the appropriate browser, app or API control tool and collects each lane's original output. The [provider-run contract](provider-run-contract.md) defines durable files and states. `provider_runs.py plan` schedules owners; it makes no network or paid calls and has no built-in provider adapters.

## Before fan-out

1. Fix the decision question, the user-visible result that could change, the as-of date, the source and privacy boundary, and the condition that would make another report unnecessary. A model's report length, search count and citations are not outcomes.
2. Inventory the requested modes and the current installed Skills. Resolve the executor for each route at runtime; a `route_skill` in `study.json` is a hint to check, not an adapter the planner executes. Preserve a shared question and evidence standard in every prompt; add a mode-specific request where it has a real advantage. Record each exact prompt in `study.json`. If the question names one specific page or document, archive that original and verify how each isolated provider receives it under [Seed source handoff](provider-run-contract.md#seed-source-handoff). A model name or the words “Deep Research” inside a prompt do not prove the native research mode was used.
3. Check provider authorization separately for every paid route **and every metered subtool that an autonomous Work lane could choose**. A lane in `study.json` or in the dispatch board is a plan, not permission to purchase or to expose private sources. A no-spend sentence in the prompt cannot enforce a per-call cap; if the task cannot constrain the tool set or pause before charging, defer that lane without a task-specific spend authorization while the authorized lanes proceed.
4. Run `provider_runs.py plan <study-dir>` and use its `parallel_groups` as owner packets. Each queue groups the lanes that use one control surface; its cards contain the exact prompt, provider, mode, decision question and current state. Assign one owner to each surface queue before any external submission. Do not hand the same lane or live surface to two agents.

The planner defaults `control_surface` to the provider name, keeping two modes of a shared app or account with one owner. Set an explicit distinct surface only after verifying that the tabs, TaskSpaces, app instances or API clients can be controlled independently. A parallel group defaults to at most three surface owners. Its queue includes both active and new lanes on that surface; `owner_reconciliation_required=true` means the coordinator must reuse the active owner or confirm that owner has released UI control before assigning another. Each owner performs UI actions for its queue in order, but can submit a second mode after the first asynchronous job is accepted without waiting for its report. A human using the same live UI takes priority; check occupancy before automation and stop manipulating that surface if its state is overwritten.

## Execute and collect

- Use the host's available subagents for independent surface queues when explicitly requested or otherwise authorized by the host's delegation rules. Assign exact files, route, surface, and responsibility; owners must know they share the workspace and must not overwrite another queue's files. Without subagents, make independent tool calls concurrently where the host supports it, then serialize actions sharing a UI surface. Do not force parallelism when it adds no evidence or risks losing a live session.
- Start long asynchronous routes early. On provider acceptance, immediately record `submitted` with the real task ID or conversation URL and preserve the raw create response. A provider's `processing` result becomes `running`. A timed-out create is `failed_unknown` until the existing task can be queried; do not create a second paid task to fill the board.
- For each UI route, read back the actual selected mode **before** sending. Keep a screenshot or comparable UI/API receipt when ordinary chat and native Deep Research can be confused. For app plugins, retain the tool return files; a generated narrative is not the plugin's raw response.
- Save each original report under a lane-specific `sources/` path without editing it, then append `collected` with that file. Compare its named subject and source access claim with the user's archived seed before using article-specific findings. A completed native research mode can still research a different article; preserve that output with a mismatch note and exclude it from evidence synthesis. Run `validate` before synthesis. `plan` puts `submitted`/`running` lanes in `active_query_existing_origin`, `collected` lanes in `collected`, and deferred/uncertain lanes in `held_no_auto_retry`; these are coordination states, not factual confidence scores.
- Ask an active lane for its existing result while other lanes run. A slow or unavailable lane need not block synthesis once the decision question has enough fit-for-purpose source evidence. State the missing perspective and leave its true status in the ledger. If its later output changes a claim, revise the synthesis from original sources.

## Synthesize across routes

Create a claim-by-source matrix rather than voting over provider conclusions. Record which lane first surfaced a claim, the underlying original URL or document, its date, what the source can observe, a counterexample, and verification status. Several reports citing one vendor page form **one evidence family**. Different models can make correlated errors; agreement is a reason to inspect the original, not proof. See [Kim et al., *Correlated Errors in Large Language Models*](https://arxiv.org/abs/2506.07962) for an empirical warning on cross-model error correlation.

Compare the modes by **incremental decision value**: which original evidence did a route add, which prior claim did it overturn, and which business question remains unanswered? Reopen every decisive original before promoting the claim into P3's citation registry. Keep source assertions separate from provider inference and from customer evidence. Finish with what action or product decision the verified evidence supports, what would falsify it, and which real user outcome is still unobserved.

## Skill composition, not a provider roster

The coordinator selects the needed routes from the current catalog and records their provider, mode, exact prompt, optional `route_skill`, and control surface in `study.json`. One surface owner may run several modes through one provider Skill; another owner can run an asynchronous API Skill at the same time. The coordinator can also compose favorites or prior-work retrieval **before** choosing a new external method, browser/app control for UI execution, and source-verification Skills after collection. No provider name or task sequence is compiled into the planner; a future route adds a lane and an executor Skill without changing the ledger schema or synthesis rules.

For example, an ordinary chat can challenge the question, a native Deep Research route can search broadly, a data-plugin route can return structured records, and an asynchronous API route can produce a long report. The actual route might be `kimi-use`, `unifuncs-router` plus its specialist, or a browser Skill; read the current Skill rather than copying commands from this example. Keep mode-specific successes in those provider Skills. Select lanes by the decision, available rights and cost. The underlying source, not the number of routes, decides whether a business claim is established.
