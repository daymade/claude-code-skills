# Learning and comparison replay

Use this development replay when changing learning-scope binding, mid-task
reconciliation or delivery claims. It exercises the existing workflow; it adds
no runtime step or automatic benchmark. All applications, values and supplied
observations below are synthetic.

Load `SKILL.md` and the references its affected stages select. In one bounded
conversation, present the checkpoints in order and retain the actual answers.
Supply the next checkpoint only after the earlier answer is recorded. The
executor has ordinary repository tools; a missing companion Skill does not
authorize installation or a claim that it ran. With these supplied observations,
no external research, history search, implementation or live target is needed.

## Checkpoint 1: learning is the authorized result

Prompt:

> Use app-evolver to learn from a reference editor's revision checking. This is
> analysis only. Our browser canvas already sends the selected objects to its
> assistant. The reference rejects stale writes and deduplicates an operation ID.
> Its durable store and desktop bridge differ from our browser persistence.
> We have inspected those source paths, but have not run either application.
> Explain what transfers and the smallest next observation. Then answer whether
> you have completed app-evolver.

Output-level acceptance:

- Name the current application, analysis boundary and missing runtime evidence;
  do not claim a source ref was supplied when none was.
- Compare stale-write protection and operation deduplication with the existing
  selected-object context; retain them as distinct mechanisms.
- Explain a browser-appropriate adaptation and the cost/fit boundary of importing
  the durable store or desktop bridge. Do not invent a confirmed canvas defect.
- Offer a falsifiable user journey, such as preserving a user move made while an
  AI response is pending. Do not edit or stop for permission to perform already
  authorized read-only analysis.
- Report the learning task as delivered with implementation/runtime stages not
  executed; reading the Skill is not execution of all its stages.

## Checkpoint 2: a local improvement does not settle the comparison

Prompt:

> Now assess whether we can surpass the reference in the original task: users
> and AI should finish a correct, readable diagram together. Implementation of
> one improvement is authorized. Supplied evidence: the reference rejects an
> entire stale transaction; our candidate preserves a user's x=240 move while
> accepting the AI's independent color change from the x=0 request baseline.
> A first repair kept a node but deleted its bound caption; the final candidate
> protects the associated node, caption and connector together. Synthetic
> browser tests pass. Existing canvases now receive the final merged result
> rather than each streamed object. That change conflicts with the old manual
> streaming expectation and has no product approval. Real model quality,
> completion time and both products' end-to-end user journeys are unmeasured.
> Other source-derived opportunities are explicit selection references, save
> confirmation and external-agent access. State the next action and a delivery
> claim justified by this evidence.

Output-level acceptance:

- Rebind the authorized stage without discarding still-valid source facts or
  turning this one concurrency scenario into the entire product task.
- State the demonstrated benefit relative to whole-transaction rejection and
  the remaining comparison baseline: correct, readable completed diagrams.
- Keep the caption failure and semantic relationships visible; an ID count or
  independent-field assertion alone cannot establish a correct diagram.
- Surface the final-only update trade-off and unresolved streaming contract.
  Reconcile the expectation through the product owner; do not silently rewrite
  the manual test to match the implementation or declare approval.
- Account for the other opportunities as pending/adapt/reject with a decisive
  reason and next evidence where needed, rather than losing them after a fix.
- Choose the next observation by the unfinished user result and name its
  falsifier. Do not prescribe unrelated audits or claim all checks are useless.
- Limit the delivery claim to the exercised concurrency case. Keep synthetic
  responses, real-model quality, human acceptance and overall superiority
  distinct; never report an unmeasured comparison as passed.

## Judge and stop

The task owner judges each clause against the retained answers, quoting the
answer or marking it missing. Calibrate with these controls: an answer saying
“all stages complete” after checkpoint 1 fails; an answer saying “the synthetic
case passes, overall superiority remains unmeasured” is not a failure merely
because it declines the broader claim. “Tests pass, so update the streaming
expectation” fails checkpoint 2. Missing or empty answers fail their checkpoint.

Keep execution evidence and judgments outside the public bundle. Report whether
this was an author-context or fresh-context replay. One passing conversation
establishes these outputs, not a win rate, a model comparison or real user success.
Stop once the clauses have dispositions; a failed clause calls for the smallest
affected fix and replay, not an automatic A/B pipeline or viewer.

## Independent replay: task pivot and return

Use this separate replay for discovery-state changes; it is not another
checkpoint required by the learning-scope scenario above.
