# Evidence and fit

## Establish a usable baseline

Trace the user journey through entry, execution, persistence and downstream
consumption. Inspect the current implementation and representative existing
tests before asserting a gap. Separate a proven defect from a proposed benefit.
Record the source ref and runtime identity beside any observation that depends
on them; old history locates evidence but cannot establish current behavior.

Resolve available capability owners by job. Reuse research, history readers,
requirements, engineering, visual QA and release workflows rather than copying
their engines or volatile configuration into this Skill. A dependency name is
not proof that its runtime is installed or usable. Probe the prerequisite needed
by the chosen path, perform authorized preparation and resume its original job.

## Reconsider interface structure

Use this check when the user questions navigation, information hierarchy or the
coherence of an existing interface. Keep an isolated cosmetic defect narrow.
The executing coordinator performs the comparison; no generic layout score
decides whether the information belongs at the right level.

1. Name the actor's real task and the objects needed to finish it. Map each
   current entry to its object, task, scope and return destination. Distinguish
   everyday work from setup, operations, examples and diagnostics without
   assuming that every function deserves a peer navigation item.
2. Compare the current grouping with one plausible alternative using the same
   representative content and required capabilities. Show which information is
   persistent or disclosed on demand, what the actor sees first, and how they
   enter, inspect evidence, act and return. Keep important uncertainty visible;
   removing qualifiers or hiding necessary work cannot improve this comparison.
3. Select from observed task friction: unclear ownership, repeated context,
   cross-area searching, lost position or a misleading next action. Retain the
   current structure if it serves the task better; fewer tabs, breadcrumbs,
   working clicks and readable text alone do not settle the structural question.
4. Carry the selected design idea through that complete path, including list,
   detail, original evidence, history and relevant empty/error states. Use visual
   treatment to express those relationships, rather than giving only the first
   screen a new skin. Preserve object/version identity, drafts and return context
   wherever the existing product promises them.

Stop the comparison once evidence selects an authorized increment. Keep a
reversible grouping assumption distinct from a user-approved product decision;
leave missing user judgment explicit. Do not add a new product entity, remove a
supported job or broaden implementation authority to make the layout convenient.
Verify the affected path through the existing acceptance owner after implementing
it; a coherent concept is a proposal until its actual use has been checked.

## Mine experience without manufacturing authority

Use authorized, physically bounded sessions or indexed candidates. Preserve:

- User requirement or correction and its position in the session.
- Executor action and exact input/ref.
- Tool result or independent observation, including failure and recovery.
- Agent's assigned task and returned evidence, distinguishing assertion from probe.
- Final accepted outcome, or the explicit lack of human acceptance.

For matched successes and failures, ask what changed the outcome: input,
implementation, environment, measurement or the interpretation of the task.
Do not promote every incident to a universal prohibition. A reusable rule needs
a scope, triggering condition, evidence and exit condition; keep project facts
with their application. Never infer access to private internal reasoning from
access to a session's visible messages or tool traces.

Keep raw history and provenance in authorized private locations. Publish only
generic decision rules and synthetic examples. State the searched providers,
selected sessions and coverage gaps; a ranked subset is not a complete census.

## Analyze mechanisms, not popularity

For each promising competitor path, inspect:

1. Trigger and assumptions: what the user does and what must already exist.
2. Normal completion: output, persistence and how the consumer receives it.
3. Failure and recovery: timeout, cancellation, partial data and retries.
4. Ownership: process, data, provider, identity and state boundaries.
5. Adoption conditions: dependencies, resources, license terms and operating cost.

Locate code with ref-bound file/line evidence or use dated primary product
evidence. A README, screenshot, benchmark or star count supports only what it
actually shows. If one path is inaccessible, use another permitted source that
can answer the same question; keep the original observation unknown when it
cannot. Do not substitute a neighboring fact for the required evidence.

Compare the mechanism with the target's existing equivalent. An attractive
queue, remote inference service or permissive fallback can be correct in its
source app and unsuitable in a local-first app or strict evidence pipeline.
Prefer adapting a small boundary over importing the whole system.

## Make the disposition operational

Use the decision table in [the entry](../SKILL.md#3-decide-what-transfers).
Prioritize the smallest change that improves the selected result without moving
an unresolved assumption into an implementation requirement. If a hypothesis
can be checked now, check it. Otherwise make it the subject of a bounded probe
or a user question rather than a scheduled feature.

When choosing the next increment, treat confirmed evidence and permission to act
as admission conditions. Rank admitted work by the unfinished user result it
unlocks. An uncertain blocker on that path calls for a bounded probe; it does
not make an easier unrelated repair more valuable. The executor makes this
judgment; no checklist score establishes business priority.

Use these synthetic replay cases when a repair batch ends or the user questions
the direction. Stop after the next action names the missing observation and its
falsifier; do not launch another audit merely to fill the queue.

| Current evidence | Next useful action | Invalid substitute |
|---|---|---|
| Confirmed repairs are delivered; the user still cannot identify how the real task's contributions combine; no new failure is observed | Inspect that task's actual contribution/result path and identify the concrete missing result | Add a new module-wide boundary audit because it is easy to prove |
| The real intervention path reproduces an already-authorized duplicate-write defect | Repair that defect with failure and healthy controls, then return to the same intervention path | Declare all technical checks unnecessary, or count the repair as the complete collaboration outcome |

Synthetic example: an enrichment stage delays a completed draft. Adapt the
competitor's phase separation if the target contract allows a usable draft before
enrichment. Preserve strict review if review is required before publication.
Determine the budget from that application's measured use; do not universalize
a duration observed elsewhere.

Continue with [implementation and acceptance](implementation-and-acceptance.md)
once evidence selects an authorized increment.
