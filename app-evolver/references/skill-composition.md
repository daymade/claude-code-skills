# Compose Skills around the evidence gap

Use this reference during [evidence gathering](../SKILL.md#2-ground-opportunities-and-constraints).
Keep the specialist responsible for its own methods and dependencies; keep
app-evolver responsible for product fit, authorized changes and user acceptance.
Do not replace the existing workflow with a reverse-engineering framework.

For a named feature or function investigation, read
[feature investigation](feature-investigation.md) before the specialist handoff.
Use its anchor selection and evidence notes with the selected owner's available
tools; it requires no Eleven application, ACP adapter or additional MCP server.

## Select the owner

| Input or unfinished result | Skill route | Boundary |
|---|---|---|
| Complete source repository; architecture or feature implementation | Existing `competitors-analysis` and repository tools | Continue the established source path; REA is unnecessary unless a claim requires shipped-artifact or runtime evidence |
| Released application, ASAR/JavaScript/Electron, native/managed package, or passive runtime evidence | [`reverse-engineer-anything` from REA](https://github.com/morluto/rea/blob/main/.agents/skills/reverse-engineer-anything/SKILL.md) | Use its target-specific guides and actual available capabilities; instructions alone do not connect analysis tools |
| A specialized APK, JS, protocol, native or security-analysis question | [`reverse-skill`](https://github.com/zhaoxuya520/reverse-skill/blob/main/skills/SKILL.md), or its [`reverse-skill-router` adapter](https://github.com/zhaoxuya520/reverse-skill/blob/main/plugins/reverse-skill/skills/reverse-skill-router/SKILL.md) | Load only the selected specialist and necessary resources; the adapter requires its canonical repository context |
| Recovering a buildable source project from a package | Available `find-lost-code` or an equivalent recovery Skill | Use only when reconstruction is the requested result; this optional local owner is not a public-reader prerequisite |

Resolve the installed entry through the host's actual Skill inventory. If absent,
read the linked canonical public entry and its relevant linked resources for
method selection. Record the revision consulted when it determines the next
action. Do not call an unavailable Skill or treat reading its instructions as
successful execution. Do not embed a copied upstream router or install every
module to satisfy one question.

## Keep personal discovery optional

For a public consumer without a favorites library, start with the public routes
above. No private path, account, collection, subscription or private Skill is
required. For a user with authorized collections, invoke their available
`favorites-search` to supplement mechanisms or discover another relevant
framework. Keep explicitly requested research lanes and their coverage limits;
do not report a required unavailable lookup as completed.

Evaluate a newly found framework by its actual entry, supported inputs, evidence
outputs and fit before choosing it. Use it only for the current evidence gap.
A favorite is a discovery signal, not evidence of correctness or permission to
install it. Personal research remains outside this distributed bundle.

## Execute a bounded handoff

The executor supplies the specialist with:

1. The current application contract and exact target artifact/ref.
2. The feature question and missing evidence, with the existing baseline.
3. The authorized observation/execution scope and protected data/behavior.
4. The expected findings: source locations or evidence IDs, observations,
   inferences, unknowns, failure/recovery behavior and coverage limits.

Follow the chosen Skill's current interfaces and relevant guides. An available
REA instruction bundle is distinct from its CLI/MCP runtime and analysis engine.
Use available authorized tools; when a required runtime is missing, report its
exact dependent gap and continue independent work. Skill-only integration does
not authorize configuration writes, downloads or engine installation. Prepare
dependencies only under a separate applicable setup authorization.

Return findings to [the mechanism decision](../SKILL.md#3-decide-what-transfers),
then the original implementation and acceptance stages. Keep architecture
reading, copying implementation and distribution permission separate. Treat a
specialist's assertions as hypotheses until supported by its original evidence;
decompiled pseudocode or static structure is not observed runtime behavior.

## Verify composition and stop

For an affected task, check that the requested question received usable evidence
or an explicit unknown, that its next engineering action follows the product
contract, and that the original healthy path and acceptance still work. Check
public use without favorites, complete-source use without unnecessary reverse
setup, and a missing-runtime case without automatic installation or fake success.
Use the host's actual capabilities for task-result evidence; link checks prove
only source reachability.

Keep the selected Skill source and unresolved prerequisite for resume. Continue
from the first unmet observation after it becomes available. Stop once the
evidence resolves the question and the authorized original result is delivered;
do not expand into full-app reconstruction or another framework merely because
it exists.
