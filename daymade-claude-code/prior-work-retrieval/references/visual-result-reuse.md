# Reusing a visual result

Use this during candidate verification when the user names an older diagram,
page, chart or deck to reuse or improve. It adds no search carriers or new receipt;
keep the existing retrieval and adoption reason.

Open the named rendered artifact and the current candidate. Read the relevant
generator/layout source after seeing what it produced. A matching filename or
reused source proves identity/reuse of code, not retention of effective visual
decisions. If a rendered original is unavailable, state the limit and use the
available source without calling its visual quality verified.

Separate the decisions in the existing adoption reason:

| Decision | Evidence |
|---|---|
| Facts to retain or replace | Current user decision and authoritative data; mark outdated addresses, relationships and deployment states as superseded |
| Visual behavior to adapt | What the actual old rendering makes easier to read: hierarchy, density, typography, grouping or routing; identify the corresponding source when available |
| Style acceptance | What the user actually endorsed; “the new one is worse” does not mean “freeze the old style”, and a delivered file is not automatically an approved template |

The executor compares the images and records concrete observations. A reviewer
may expose an unreadable path or a missing entity; it cannot certify the user's
aesthetic acceptance. Keep the rendered before/after available in the current
task; no generic image metric enforces these judgments.

## Synthetic contrast case

Request: “The earlier architecture diagram is clearer. Use what worked, but a
better design is welcome.”

- Incomplete adoption: copy the old generator, enlarge all boxes and produce a
  new figure with no element overlaps. This verifies code reuse and collision
  avoidance while leaving the requested visual improvement unobserved.
- Actionable adoption: compare both rendered diagrams, identify that role lanes
  and restrained annotations made the earlier path readable, adapt those
  decisions, and regenerate using current connections and statuses. Show the
  new result; leave user taste acceptance open until the user responds.

For a local factual addition after the visual direction is established, preserve
unaffected identities and reading paths, inspect the changed area and the full
render, and avoid restarting retrieval or redesign solely because another node
was added. A new explicit request for earlier work still follows the normal trigger.
