# Example Session: 录音笔 → 妙记转写稿修正（四人对话 · 品牌名链条 · dashboard 结案）

以下是**完全合成的演练 fixture**：名称、话语、数量和时间均为虚构，不对应任何真实人物、项目或逐字稿。它只演示三个可复用判断模式：**文内自证链**、**二遍裁决的拒绝判据**、**enqueue 粒度决定 dashboard 裁决质量**。

## 场景与格式识别

假设一份录音笔音频上传妙记后导出为：

```
<date>|<duration>

Keywords:
民宿品牌、预订平台、在地故事

Transcript:
说话人甲 00:00
我们先拆解这次民宿品牌的任务。
```

要点：`说话人 HH:MM` 标签行已经人工确认，是身份 SSOT，纠错全程不改。`Keywords` 同样来自 ASR，也在纠错范围内；metadata 中的实体若写错，未来检索会静默失败。

## Stage 1：applied 0 是正常的

合成运行返回 `applied: 0, deferred: 1`。字典面对全新语境可以零命中，剩余工作仍由 Native AI pass 完成。唯一 deferred 是项目规则 `轻蓝→青岚` 命中正文「这套墙面偏轻蓝色」；这里说的是颜色，native pass 应判 `kept_original`。**deferred 不是待应用清单，而是待裁决清单。**

## 文内自证链（高置信修正的判据）

同音或近音 + **同一文件已有正确写法** = confident fix，不必跳到外部搜索：

| 合成 ASR 碎片 | 合成正解 | 自证锚点 |
|---|---|---|
| 云栈院 / 云展苑 / 云站苑 | 云栈苑 | 同文多处写对，且上下文始终指同一虚构品牌 |
| 大牛 / 大六 | 阿牛哥 | 同文中说话人逐字拼出虚构账号名；「大牛」是常用词，只在该上下文修 |
| 十楼村 | 石楼村 | 同文另一段已写对虚构村名 |
| 再地 | 在地 | 同文已有「在地故事」，且它是行业术语 |
| 可定 | 可订 | 预订平台语境 |
| 嫁个机位 | 架个机位 | 拍摄设备语境 |

**词典沉淀的边界**：from 侧是非词或罕见形时才 `--add --domain`（如 `云展苑→云栈苑`）。from 侧是常用真实词时，放入 domain context 作 trap，由上下文裁决；把「大牛」做成无条件字典规则会误伤正常表达。

## 二遍冷读：候选必须逐条裁决

独立冷读只负责提出候选，不负责替用户下结论。三类典型拒绝判据：

- **拒 `like → Lite`**：`like` 在口语中成立，而且同一引擎刚在邻近位置正确识别过 `Light`。这是 ASR capability counter-check，不该强改。
- **拒 `做皮了 → 做疲了`**：下文明确使用「皮实」解释该说法；可理解的真实口语不改。
- **拒 `云豆宝宝 → 芸豆宝宝`**：虚构作品名可能故意用「云」做双关；命名意图无法证伪时保留。

接受项应同时满足近音关系和文件内锚点，例如「分别→分辨」在同句型的另一处已写对；「石库→石窟」在同文景点清单中已有正确写法。

## enqueue 粒度决定 dashboard 裁决质量

合成失败 fixture：若 enqueue 的 `original` 错放整句「我们今天先看云展苑那间房」，而人工 override 只填「云栈苑」，file edit 会把整句缩成一个品牌名，吞掉上下文。防线分三层：

1. **enqueue 粒度**：`original` 只放 ASR 误写词「云展苑」，整句放 `context`——[native_ai_full_workflow.md](native_ai_full_workflow.md) step 7 给出完整 payload。
2. **dashboard UI**：override 输入框上方显示实际替换范围；输入远短于原文时给出警告。
3. **裁决后抽查**：批量裁决后逐行核验落地，并抽读关键行语义，而不是只看队列状态变成 closed。

## 收尾复利

- 稳定的非词误识进入项目 domain 字典；常用词陷阱进入 context file。
- 同一虚构品牌的多种 ASR 写法统一回填后，下次 Stage 1 可以直接处理。
- queue 中每条 item 都有 disposition；`skipped` 项写入项目上下文，等待下一份录音提供新证据。
