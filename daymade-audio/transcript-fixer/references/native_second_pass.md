# Cold review, adjudication and recovery

Step numbers refer to [the native sequence](native_ai_full_workflow.md); ladder
rungs refer to [entity triage](native_entity_triage.md).

Read before Full-tier cold review or recovery from an unfinished review. Use the existing [packet owner](native_review_packets.md) for split, batch and resumed assignments. Historical examples are optional [evidence](native_historical_evidence.md).

6. **Second pass — catch what one read missed.** For split, multi-file, or resumed Full reviews, follow [Native review packets and recovery](native_review_packets.md): freeze the complete expected file set, validate every returned span before editing, and resume only missing or failed assignments. Use that reference's JSON result contract in place of the compact-table template below. Single unsplit reviews may keep the table workflow.

   A single linear read reliably leaves residue: an idiom degraded into a near-homophone, a term wrong in just one spot among many correct ones, an acronym misheard as another. Always re-scan once for leftovers. A cheap targeted variant comes first: **trap-scan** — scan the file for every trap pattern the domain's context file documents (the recurring homophones this domain is known to produce). Resolve the file through the [context location](domain_context_guide.md#location), then run the scanner rather than truncating a manual per-trap grep list:

   ```bash
   uv run scripts/fix_transcription.py --scan-traps \
     --context-file "<domain-context.md>" -i meeting.md
   ```

   Every documented trap comes back with line number + context window, confirmed-correct records (`**X = 真实实体，勿修**`) are reported as keep-as-is so you stop re-investigating settled questions, and the no-hit list makes "scanned and absent" distinguishable from "never scanned". A clean trap-scan plus your first pass is enough for fast tier. For a long or high-stakes transcript, *also* spawn an independent subagent (Task) to re-read the corrected file cold — fresh eyes with no memory of your first pass catch what you've read past. **The subagent's job is to *return a residual list*, not to re-narrate the transcript.** Give it an output format and a hard cap, because a subagent that thinks aloud line-by-line will blow its own context window before finishing (one real second-pass run on a 1131-line transcript hit the 32k token ceiling mid-scan and returned nothing usable). The correct prompt shape:
   - Scope it to one file or one assigned packet; forbid editing and cross-file grep.
   - Hand it explicitly confirmed verdicts as a do-not-re-report list. Already-applied first-pass edits without that confirmation remain reviewable against raw evidence; use the [synthetic occurrence controls](native_review_packets.md#occurrence-specific-evidence) when preparing a replay.
   - For a single unsplit review, demand a compact table only — `line | original ≤20 chars | suspected | one-line reason | confidence` — and tell it to stop after the list, no prose preamble, no per-line stream-of-consciousness, no re-deriving corrections it has already made.
   - **Write the delivery protocol into the prompt's tail when the reviewer runs in the background** (the shape long second-pass reads take in this harness): "when done, call SendMessage to send the final table back to the main session — going silently idle counts as unfinished," plus "reply 'received, ETA N minutes' when you start." A background second-pass prompt without it leaves the main session blind-polling a silent agent . A foreground Task needs none of this — its final message is the delivery.
   For text that exceeds a bounded read, use [Native review packets and recovery](native_review_packets.md) for segmentation and validated aggregation. Assign the generated packet with its file-absolute line numbers; do not replace complete coverage with a deliberation cap or hand-maintain another split threshold.
   A silent reviewer past its ETA is not a dead reviewer: send ONE SendMessage nudge first — it resumes from its own transcript at zero rework cost (measured 2026-09-04: three background reviewers went silently idle; one nudge revived all three). Only when a second ETA passes without response do you enter the fresh-retry / salvage path below. **Completion requires a usable review result, not merely a successful process status.** The reviewer must cover the whole file — under the split regime above, each reviewer must cover its whole assigned segment and the segments together the whole file — and return the result format assigned for its route (packet JSON, or a table/explicit `no new residuals` for a single unsplit review); an empty, malformed, or truncated response is a failed pass and must be retried with a fresh reviewer. A retryable subagent failure does not satisfy this pass either. If the failure says it is retryable or provides a retry delay (for example an HTTP timeout with `retry_after`), wait at least that long and retry the fresh-context review. Only treat the subagent path as unavailable when the tool truly cannot run (for example, these instructions are already executing inside a subagent that cannot spawn another). A targeted trap-scan or grep for known variants remains useful, but **it is not an independent re-read**: it can confirm that known error families are gone and structurally cannot discover the first reader's blind spots. In one production run, replacing a timed-out fresh review with known-pattern grep reported clean; retrying the cold review surfaced 26 additional candidates.
   **Salvage is legitimate when the dead reviewer's transcript holds the complete analysis.** If the reviewer died on an infra error or a token-ceiling truncation *after* its transcript shows a complete candidate list with per-item reasoning — the analysis finished, only the final table never shipped — you may extract the candidates from that transcript instead of re-spawning, under these conditions, all required: ① every extracted candidate still goes through step-4 triage and the accept/reject heuristics below — you adjudicate; the dead agent only surfaced; ② the salvage is recorded where the run's corrections are recorded (the `asr_note` line / your summary), because a salvaged pass is not the same evidence as a completed cold read; ③ **"complete" must be evidenced, not assumed** — the candidates must reference content from the file's final stretch (or each segment's end), or the transcript must show it read through to the end; a list that stops at line 1500 of a 3043-line file is a *partial* analysis and a failed pass — retry fresh. Where the transcript is: the Agent/Task spawn result's `output_file` path is the reviewer's JSONL transcript; if you lost it, the main session's own `~/.claude/projects/<project-slug>/<session-id>.jsonl` contains the reviewer's records as `isSidechain: true` entries keyed by its `agentId`. 
   Then adjudicate each residual — the subagent's list is **candidates, not conclusions** (one real run: 10 rows → 4 accepted). Run each through step-4 triage, plus these heuristics, all production-validated:
   Apply [occurrence-specific evidence](native_review_packets.md#occurrence-specific-evidence) before the self-proof heuristic: another speaker's standard terminology does not prove an earlier utterance's pronunciation, and a participant identity does not prove the spoken nickname/address. Same-file wording must discriminate this occurrence through its referent or explicit meaning; fluency alone cannot do that. Covered audio retaining the original outweighs an unsupported sound-changing normalization. Homophonic spelling still needs the occurrence's written or semantic evidence.
   - **Accept — near-homophone + in-document self-proof.** `利智回购`→`离职回购` when the same table of contents a few lines earlier already reads `离职回购`: near-sound plus the correct form inside the same file settles it — **provided the proof occurrence is verified in the raw text** (an occurrence written by the same upstream pass proves nothing: judge and judged sharing a source is circular) **and only one candidate occurs correctly** (both occurring = non-discriminating proof; fall back to phonetic minimality or the queue). Referent-locked homophones likewise (`他`→`它` when the antecedent is a document, not a person).
   - **Reject — sound distance falsifies too.** The sound test cuts both ways: near-sound is evidence *for* a fix (step 4); implausible-sound is evidence *against*. `代号`→`代码` (hào/mǎ) and `一撮`→`一坨` (cuō/tuó) are not swaps ASR makes — that candidate is the reviewer over-reading, not the engine mishearing. **The exception is step 4's cross-language proper-noun class**: a foreign name spoken inside another language can legitimately land far from its canonical sound. Don't reject those here — route them to the queue for audio verification instead. The exception is defined by *kind*, not by rarity, and it takes **both** of step 4's conditions: the candidate is a proper noun that could have been spoken in a different language from the one being transcribed, **and** it sits in the slot of someone the project already knows. Both → route it to the queue whatever the sound distance. Either one missing → this rejection rule applies, as it does to every common word and every same-language homophone. **When the sound test itself is in doubt, stop reasoning about acoustics and measure them** — if rung 7 is authorized, cross-family agreement supplies stronger evidence about sound distance than your intuition about what “ASR would do.”
   - **Reject — the ASR-capability counter-check (a strong prior, not a proof).** If the same engine rendered the word correctly elsewhere in the same transcript, the word is demonstrably inside this engine's recognition range for this audio — so a different rendering nearby is *more likely* what the speaker actually said, and the bar for "fixing" it jumps. (Candidate `一条`→`一坨`: `一坨` was recognized correctly a few lines earlier, and `一条` is itself a colloquially valid measure phrase — the two together reject the fix.) Keep it probabilistic: the same engine genuinely can shatter one name into a dozen variants (see Project-Specific corrections) — the counter-check weighs most when both the correct form and the candidate are common words the engine handles routinely, least when they're rare proper nouns. **When it collides with the in-document self-proof, it loses by default — because the two rules fire on the identical fact.** Both are triggered by *the intended word appears correctly elsewhere in this transcript*: the self-proof (accept heuristic above, and the priority note under **Prefer the smallest edit**) reads that as evidence **for** the fix; this counter-check reads the same observation as evidence **against** it. They cannot both govern, so decide on the *disputed* rendering rather than on the proof: **is the text as transcribed coherent in its own slot?** `一条` inside `一条视频` is a valid measure phrase right there → counter-check wins, leave it. `利智回购` is not a phrase at all → self-proof wins, fix it. Being a real word *somewhere* is not the test; being readable *here* is — and an English token or a common noun passes the first test while failing the second all the time. Tighter still: when the correct form occurs **in the same line** as the disputed one, treat the self-proof as controlling unless the disputed rendering reads cleanly in place. (2026-09-18, a real cost: a cold-read reviewer proposed `我的 id`→`我的 AI`, then withdrew it under this counter-check because the engine had rendered `AI` correctly ~20 times across the file. But an `id` cannot 看懂 anything, the very same line already read `我的 AI 也没有这些上下文的`, and the whole passage was about whether an AI could understand a handoff. The self-proof owned that call; the withdrawal was logged in the run's `asr_note` as a correct use of the counter-check, so the error survived two passes and shipped. A withdrawal under this rule is itself a judgement — record *why the self-proof did not apply*, not merely that the counter-check fired.)
   - **Reject — intelligible real words.** `一撮` is a perfectly good measure word; don't rewrite readable speech just to make a running metaphor consistent. Only fix what the speaker plausibly didn't say.
   - **Reject — evidence-free reconstruction.** A proposed fix with no phonetic basis (`半`→`分`) is a guess about meaning, not a correction.
   - **Minimal edit.** Fix the misrecognized word; never insert unspoken words (`打完`→`打算` ✓; rewriting as `打算怎么` inserts a `怎么` the speaker never uttered ✗).
   - **Prefer the smallest edit that explains the error — rank candidates by phonetic distance before you judge any of them.** The rule above bounds how *much* one candidate may change; this one decides *which* candidate wins when several would read fine. ASR errors are small perturbations — the engine maps a heard sound to the nearest word it knows — so among candidates that all make sense, the one changing the fewest phonemes is almost always what was said. Useful fingerprint in Mandarin: **a reduplicated or multi-syllable tail surviving intact while only the leading syllable differs** points at an initial-consonant confusion (retroflex/alveolar `sh`/`s`, `zh`/`z`, `ch`/`c`, and the `n`/`l`, `f`/`h` pairs), so search same-final/different-initial candidates *before* concluding the whole word was misheard.
     **Where this fails is not while you generate candidates — it's while you audit text that is already there** (an upstream correction, or a fix you accepted on the first pass). Reviewing existing text puts you in verify-mode: you ask "is this reasonable?", it is, and you move on — never noticing you were handed one candidate rather than a ranked set. A candidate that rewrites three syllables can be perfectly idiomatic *and* be a rewrite; the only thing that separates it from the one-phoneme candidate is that you generated both and compared. So when auditing any already-applied correction, force the question: **is there a smaller edit that also explains this?** If you cannot answer it, you have validated rather than verified. **One priority outranks phonetic minimality: the in-document self-proof — the intended word occurs correctly elsewhere in the passage, the passage is *about* that referent, and the proof occurrences check out against the raw text** (occurrences written by the same upstream pass prove nothing — judge and judged sharing a source is circular). If both candidates occur correctly, the proof is non-discriminating; fall back to phonetic minimality or the queue. And when the fix under audit is rule-backed, a raw-verified self-proof against it *is* the affirmative evidence step 2's revert bar asks for — revert, then retire or scope the rule there. 
   A second-pass subagent that returns 8 sharp rows beats one that returns 8000 tokens of narration every time. Task works when you're in the main context; if it truly isn't available — e.g. these instructions are themselves running inside a subagent, which can't spawn another — do one more thorough line-by-line re-read yourself from the corrected artifact. Do not substitute a known-pattern grep and call it a re-read. Never skip the second pass over a missing tool.
