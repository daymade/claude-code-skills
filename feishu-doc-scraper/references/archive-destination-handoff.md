# Archive destination handoff

Use this before permanent filing when the user asks to archive a Feishu capture.
The executing agent resolves ownership through the host archive's current rules;
the extractor does not classify sharing permission or enforce this handoff.

## Resolve the recipient before writing

1. Reuse an explicitly selected destination and any sharing restrictions. Do not
   reopen a settled choice because the current working directory belongs to
   another vault. Reading or downloading a source does not authorize sharing it.
2. When the user authorizes choosing a suitable location, inspect the available
   archive/project registry and candidate repositories' rules and indices. Match
   the material's intended use and permitted readers: personal, one project, or
   shared across projects. A third-party source or a team-related title alone
   does not establish team-sharing permission.
3. Check the proposed repository's content scope, existing copies and storage
   owner. Reuse its current taxonomy and source-of-record policy. Keep external
   templates or examples labelled as references unless the user separately
   adopts them as operating rules.
4. Bind the selected repository, relative directory, reader scope, source locator,
   retention route and destination index in the existing task notes or manifest.
   Explain the chosen location briefly, then continue within existing authority;
   routine classification does not require another permission round.

If a material ownership/sharing choice remains unresolved, continue authorized
extraction in task-private scratch and ask only for that missing choice. Do not
upload to a team repository by default. If the request is extraction-only, return
the capture without starting a filing or sharing workflow.

## Hand off and verify

Pass the faithful body, discussion scope, attachment inventory and unresolved
references to the host workflow. Apply the [storage contract](archive-storage-contract.md)
to the selected destination; copying an old manifest does not prove its backend
belongs to the new repository. For an existing package moving between repositories,
use the destination's established migration/storage owner and retain the source
until that owner verifies the target originals and authorized source cleanup.

Read back the filed package through the destination's normal index. Reconcile the
requested document/file set with the stored manifest and the host's retrieval
evidence. Report filing, original retention and actual-reader acceptance
separately; this handoff does not replace the existing reading-delivery gate.
