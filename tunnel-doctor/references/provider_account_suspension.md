# Provider Account Suspension（订阅活着、节点全灭的账号层故障）

## 识别特征（四联签名，缺一不可判）

1. **订阅可拉**——控制面活（订阅 API 与数据面分离）
2. **全部节点数据面测试失败**——一个都不通
3. **节点 TCP OPEN**——`nc -z` 通，只证明 IP:port 有监听
4. **TLS 握手被快速主动拒绝**——SNI 层 `tlsv1 unrecognized name`，~0.4s 返回（不是 timeout）

**对照其他「全灭」形态**：
- Step 2L（stall 型）：TCP 通但 TLS `appconnect=0.000` **挂死**（不返回）
- 域名轮换：订阅返回**新域名/新 IP**，旧节点 TCP refused 或 timeout
- 本形态：订阅返回**同一批域名**，TLS 快速拒绝 `unrecognized name`

## 诊断顺序铁律

「订阅活着 + 全节点灭」的**最常见**原因是**账号 suspended（流量超限/欠费/封停）**；域名轮换是罕见原因。

**第一个动作是查服务商账号后台**（或让用户查），60 秒定性。**禁止**先做网络层深挖——端口探测、隧道重建、订阅刷新、xray 重启，2026-10-23 实测这些花了 40+ 分钟且全部无效。

**刷新订阅对账号 suspension 结构性无效**：新节点仍走同一 suspended 账号。

## 处置

- 等计费周期重置（实例：JMS 每月 7 号太平洋时间重置）
- 或升级/更换套餐
- 或切换备用服务商
- 恢复后验证：数据面 url-test，不是「订阅能拉」

## 2026-10-23 误诊战例

完整签名在场（订阅可拉 + 6 节点全灭 + TCP OPEN + TLS `unrecognized name` 0.44s），主判断却给了「域名轮换/迁移中」。用户自己查 JMS 后台发现 `Suspended: Monthly data transfer limit exceeded 1000.004/1000 GB`。

**教训**：四联签名命中时，网络层证据再丰富也不升级为主判断；先查账号后台。
